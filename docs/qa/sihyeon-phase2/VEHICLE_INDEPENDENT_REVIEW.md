## 1. 원본 목록·이름·바이트 확인

기준 main `58eb1fad34bba957812b08cf55bdf28c5595ca60`, 최초 조사 체크포인트 `c3705d9752d6439d9b423ee162829cdafa6cf15e`를 기준으로 검사했다.

- 현재 통합 manifest의 129개 경로와 별도 소방 특수 manifest의 9개 경로를 독립적으로 합쳐 중복 제거했다. 고유 이미지 경로는 **138개**다. 기존 투명 39개를 다시 더하지 않았다.
- 구현 담당자의 `vehicle-inventory.json` 138개가 이 경로 집합과 정확히 일치한다.
- 138개 각각의 Git 기준 원본 바이트를 직접 읽어 SHA-256을 다시 계산했다. 목록의 `before.sha256`과 불일치는 **0개**였다.
- 138개의 차량 ID·한글 이름이 해당 manifest와 일치하며, 현재 파일은 모두 이미지로 디코딩됐다.
- 이 목록 검사는 새 복원 후보의 원형 보존이나 브라우저 표시 PASS가 아니다.

## 4. 공용 표시 검사에서 분리할 내용

기존 코드에서 `SihyeonVehicleDisplay.apply`는 숫자세기에 연결되어 있고, 짝맞추기·주차장·공사장·소방출동은 개별 `img` 경로를 사용한다. 숫자세기의 기본 전체 차량 선택은 `isClean` 메타데이터로 필터된다. 그러므로 원본 파일만 교체해도 모든 게임의 가시 크기가 자동으로 정규화됐다고 보고하면 안 된다.

기존 `test-vehicle-display.cjs`의 `clean.length === 39`는 1차 범위의 계약이다. 검증된 복원본이 공용 clean pool에 추가된다면 기존 39개의 바이트·이름·경계 보존과 새로 검증한 목록을 각각 검사하도록 보강해야 한다. 이 지적은 구현 담당자에게 전달했다.

## 5. 첫 복원 후보 5개 — 1254px 초기 무손실 단계

구현 담당자가 만든 전후 비교 그림에서 원본 위/후보 아래, 같은 정사각형 표시 배율을 사용한 **흰색·어두운색·격자 3개 바탕**을 각각 확인했다. 다음 다섯 파일은 새로 검수한 범위다.

| 파일 | 보존 여부를 확인한 주요 구조 | 이번 시각 검수 |
|---|---|---|
| `construction/road_roller.webp` | 앞 롤러·뒤 타이어, 거울·운전석 유리, 노란 프레임 | 차종·색·구조가 유지되며 원래 격자 사각형은 보이지 않는다. |
| `construction/asphalt_paver.webp` | 앞 호퍼·소형 바퀴·궤도·뒤 작업 장치·차양 지지대 | 큰 장비 누락과 흰 사각형·격자 잔여를 관찰하지 않았다. |
| `construction/grader.webp` | 긴 앞 프레임·중앙 블레이드·앞뒤 바퀴·운전석 | 긴 외형과 날의 위치가 유지된다. |
| `construction/backhoe_loader.webp` | 앞 버킷·유압 팔·뒤 굴착 팔과 버킷·아웃리거 | 두 종류의 작업 장치가 모두 보존되고 눈에 띄는 잘림이 없다. |
| `construction/skid_steer_loader.webp` | 앞 버킷·양측 리프트 팔·메시 캡·타이어 | 캡과 팔의 빈 공간에서 큰 불투명 격자 잔여나 잘못 지운 큰 구멍을 관찰하지 않았다. |

다섯 파일 모두에서 눈에 띄는 차체 잘림·흰 사각 배경·구워진 체크 배경·큰 투명 구멍을 발견하지 못했다. 원본과 생성 후보의 세부 픽셀은 같지 않으므로 **차체 픽셀을 완전히 동일하게 보존했다는 판정은 하지 않는다.** 위 판정은 차종·색·주요 장비 구조의 시각 보존에 한정된다.

초기 무손실 단계에 적용됐던 WebP와 Imagegen의 생성 PNG를 각각 독립 디코딩해 RGBA 바이트를 비교했다. **다섯 개 모두 1254×1254이며 디코딩한 RGBA가 정확히 일치한다.** 생성 결과를 WebP로 옮기는 과정의 추가 색·알파 손실은 확인되지 않았다. 실제 적용 파일의 SHA-256과 생성 PNG의 SHA-256은 [독립 readback 결과](vehicle-independent-first-five.json)에 별도로 보존했다.

일부 생성 결과는 alpha 1~15의 아주 옅은 픽셀이 의미 있는 차체 밖에 남아 있어 alpha>0 경계가 프레임 가장자리에 닿는다. alpha≥16·128 경계를 별도로 확인했으며, 다섯 파일 모두 프레임 가장자리에 alpha≥16 픽셀이 **0개**였다. 따라서 원시 alpha>0 bbox만으로 차체 잘림을 판정하지 않는다. `backhoe_loader`의 가시 왼쪽 여백은 5px로 작아, 표시 메타데이터에서 안전 여백을 함께 확보하도록 전달했다.

초기 exact lossless 적용본은 원본의 418×418에서 1254×1254가 되면서 파일 크기도 늘었다. 위 순서의 원본/현재 바이트는 `33,280/678,290`, `31,844/629,366`, `36,210/697,770`, `39,112/786,416`, `41,022/825,866`이다. 약 19~20배 증가를 통합 담당자와 공유했다. **실제 로딩 속도는 측정하지 않았으므로 성능 실패라고 단정하지 않는다.** 전체 자산 확장 시 모바일 다운로드·디코드 비용을 함께 확인할 필요가 있다.

## 6. 최종 배포용 첫 5개 — 768px WebP 재검수

앞 절의 파일 크기 증가를 전달한 뒤 구현 담당자는 생성 PNG를 종횡비 그대로 최대 768px로 축소하고 WebP 품질 92로 저장했다. 1254px 무손실 단계의 SHA와 최종 배포 SHA를 혼동하지 않도록 [최종 배포 독립 readback](vehicle-independent-delivery-five.json)을 따로 작성했다.

원본/생성 후보/최종 배포의 3행과 흰색/어두운색/격자 3열 비교 그림을 **5장 각각 다시 열어** 확인했다. 롤러의 거울·유리·드럼, 피니셔의 호퍼·차양 지지대·뒤 장치, 그레이더의 긴 프레임·블레이드, 백호의 앞뒤 버킷·유압 팔·지지대, 스키드 로더의 메시 캡·리프트 팔·버킷이 최종 배포 단계에서도 유지된다. 이 표시 배율에서 압축으로 생긴 눈에 띄는 흰 테두리·부품 소실·차체 잘림을 발견하지 못했다. 배경에 가까운 어두운 세부가 보이는 정도는 원래 그림의 명도 영향을 받으며, 내부 픽셀 동일성을 주장하지 않는다.

| 최종 파일 | 크기 | 바이트 | 원본 대비 배율 |
|---|---:|---:|---:|
| road_roller | 768×768 | 79,764 | 2.40배 |
| asphalt_paver | 768×768 | 87,146 | 2.74배 |
| grader | 768×768 | 95,538 | 2.64배 |
| backhoe_loader | 768×768 | 111,508 | 2.85배 |
| skid_steer_loader | 768×768 | 97,730 | 2.38배 |

별도로 생성 PNG를 같은 종횡비의 LANCZOS 축소로 읽어 최종 WebP의 알파 채널과 비교했다. **5/5 알파 바이트가 정확히 일치**하며 프레임 가장자리 alpha≥16 픽셀은 5/5에서 0개다. 이는 축소 후 인코딩의 알파 보존 근거이며 RGB 무손실이나 원본 차량 픽셀 동일성의 증거는 아니다. 백호의 alpha≥16 왼쪽 여백은 최종 3px이므로 표시 안전 여백에 관한 앞선 제안은 유지한다.

## 7. 현재 증거의 한계

- 위 결과는 원본 전수 목록·SHA·디코드, contact sheet 9장, 지정한 원본 4개의 확대 검수다.
- 신규 복원 후보의 전후 동일 배율·흰색/어두운색/격자 합성 검수는 위 **5개**에 한정된다. 나머지 이미지를 이 결과로 통과 처리하지 않는다.
- 이번 독립 작업자는 브라우저 레이아웃·게임 조작을 실행하지 않았다. 공용 Chromium 검수는 통합 담당자의 별도 기록을 확인해야 한다.
- 실제 휴대폰, 물리 손가락, 음성 실청취, 아동 사용성 검증은 하지 않았다.
- **전체 이미지 수리 완료 또는 제품 전체 PASS 판정은 아직 부여하지 않았다.**
